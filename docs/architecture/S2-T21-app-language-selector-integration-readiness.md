# S2-T21 App Language Selector Integration Readiness

Status: inactive documentation/readiness contract. No selector, copy change,
migration application, or deployment is implemented here.

Founder-approved future behavior:

- choose app language before normal first-launch onboarding;
- change app language later from Profile/Settings;
- support exactly `en` and `zh-Hant`;
- an explicitly saved preference wins over request-language detection;
- when no preference is saved, request text selects deterministic fixed-template
  language;
- safety and Solar Return templates are selected from fixed reviewed strings and
  are never translated or generated by AI.

## Existing foundation

### Shared deterministic language rules

`packages/shared/src/config/app-language.ts` defines the exact allow-list and:

- `isAppLanguagePreference`;
- `detectRequestLanguage`;
- `resolveFixedTemplateLanguage`.

`packages/shared/src/config/chat-router.ts` contains reviewed English and
Traditional Chinese fixed templates for safety and Solar Return. Persisted
preference is passed to `resolveFixedTemplateLanguage`; request text is the
fallback.

### Database and server

Migration `0035_app_language_preference.sql`:

- constrains `users.lang` to `en` or `zh-Hant`;
- uses `language_preference_set_at = null` to mean no explicit choice;
- exposes owner-scoped `update_app_language_preference(text)`;
- derives the user from `auth.uid()`;
- removes anonymous/public execution.

`supabase/functions/chat-message/index.ts` reads only the authenticated user's
`lang` and `language_preference_set_at`. It does not trust a client-supplied
language preference.

### Mobile restoration and current template use

`apps/mobile/src/services/accountState.ts` restores an explicit supported
preference only when `language_preference_set_at` is present.

`apps/mobile/App.tsx` stores the restored `appLanguagePreference` in root state.
`apps/mobile/src/services/chat.ts` uses that preference for local fixed-template
selection. There is currently no first-launch selector, Settings selector, or
language-update service.

## State and authority model

### Signed-out first launch

1. After the technical splash/bootstrap check, show the language choice before
   Auth or chart onboarding.
2. A choice is written to local app storage as a provisional preference.
3. The provisional preference controls reviewed local UI resources only.
4. It does not create an account, session, profile, chart, or server preference.
5. The gate is complete only after an explicit valid `en` or `zh-Hant` choice.

### Signed-in account

1. Restore the authenticated account before deciding preference authority.
2. If a valid explicit server preference exists, it wins over provisional local
   state and request-language detection.
3. If no server preference exists, retain the explicit first-launch choice
   locally and offer a single owner-scoped persistence attempt after session
   restoration.
4. Mark it saved only after `update_app_language_preference` succeeds.
5. Never write `users.lang` directly from mobile.

### Profile/Settings change

1. User selects one of exactly two reviewed options.
2. For a signed-in account, keep the previous saved preference authoritative
   while the narrow RPC is loading.
3. On success, update root preference state and reviewed UI resources once.
4. On failure, retain the prior saved preference, preserve account/chart state,
   announce a safe retryable error, and do not claim the change was saved.
5. A local-demo session may update local storage only and must be labelled by
   its existing local-session boundary; it cannot claim cross-device sync.

## No-network and migration-unavailable behavior

### First launch offline

- Language selection remains available because the allow-list and reviewed UI
  resources are bundled.
- Store only the provisional local choice.
- Continue only through flows that are already valid offline/local; do not fake
  authentication or server persistence.
- Fixed server templates are not invoked offline.

### Signed-in Settings offline

- Keep the last restored server preference active.
- Do not optimistically claim persistence.
- Show an accessible, language-correct retry message.
- Preserve session, profile, chart, Persona, focus, and Past Reflections.

### Migration `0035` or RPC unavailable

- Treat missing RPC/schema support as configuration unavailable, not invalid
  user input.
- Never fall back to a broad `users` update.
- Keep the existing restored preference if one exists.
- If no preference exists, keep the local provisional UI choice and clearly
  mark server sync as pending/unavailable.
- Server fixed templates continue the existing request-language fallback until
  an explicit preference can be stored.
- Language failure must not route an existing account to onboarding, reset a
  chart, create a Starter grant, or clear private state.

## Loading and error states

Required state model:

- `unresolved`: bootstrap/restoration has not established authority;
- `local_provisional`: explicit first-launch/local choice only;
- `server_loading`: narrow RPC in progress while prior authority remains active;
- `server_saved`: explicit restored or newly committed preference;
- `server_unavailable`: safe retry state; no false saved claim.

Do not replace the whole authenticated screen shell during a preference update.
Use a stable in-place control state to avoid transition/layout jumping.

Errors must be deterministic and safe. Never display or log raw Supabase
messages, SQL codes, request bodies, account/email values, tokens, URLs, or
stack traces.

## Transition invariants

- Choosing a language never clears or recreates authentication state.
- Choosing a language never clears `profileData`, `chartProfile`, Persona,
  focus, active chart version, Chat turns, or Past Reflections.
- The first-launch gate runs once for an explicit local choice and does not
  reappear merely because account restoration is temporarily unavailable.
- Signing into an account with a saved preference reconciles language without
  routing through chart creation.
- Signing out clears private account state under the existing authoritative
  logout path, but may retain the non-sensitive local language choice for the
  next signed-out screen.
- Back navigation and screen-shell ownership remain unchanged.

## Accessibility requirements

- Present choices as one radio group with exactly two radio options.
- Expose selected state, language name in its own language, role, hint, and a
  clear continue/save action.
- Announce loading, saved, offline, and failure states without moving focus to a
  hidden element.
- Support VoiceOver, TalkBack, keyboard focus, Dynamic Type, reduced motion, and
  44-point minimum targets.
- Do not rely on flags, color, or script alone to identify a language.
- On Profile/Settings save, return focus to the language row/status rather than
  resetting the screen.

## Deterministic template rules

The future selector does not alter template copy.

```text
explicit saved en      -> fixed English template
explicit saved zh-Hant -> fixed Traditional Chinese template
no saved preference    -> deterministic request-text detection
```

No case may invoke translation, generative AI, model completion, or mixed
language assembly for fixed safety or Solar Return responses.

## Claude/Fable design gate

- Profile/Settings language row, selection surface, and saved/error states;

Technical owns state authority, persistence ordering, deterministic selection,
safe errors, tests, and session/chart preservation. Visual design approval does
not authorise database or deployment changes.

## Explicit exclusions

This readiness contract adds no selector UI, translations, template copy,
migration, deployment, provider/model call, Chat redesign, account mutation,
or staging configuration. It does not change current app behavior.

## Readiness verdict

Source/data foundations exist, but implementation is not ready until:

1. Claude/Fable approves both selector surfaces and bilingual layout;
2. migration `0035` and its owner/cross-user behavior are staging-proven;
3. reviewed bilingual UI resources exist for every affected system surface;
4. local provisional storage and reconciliation tests are authorised;
5. device accessibility and account/chart-preservation evidence is defined.
